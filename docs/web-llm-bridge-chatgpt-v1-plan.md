# ChatGPT-First v1 Execution Plan

## Goal

Deliver a ChatGPT-first Web LLM Bridge that lets Codex, Visual Companion, or another caller delegate work to a stable authenticated ChatGPT conversation, select a constrained ChatGPT reasoning mode, let ChatGPT use the user's established Code MCP integration for approved local work, and return the exact run's final response plus any ChatGPT-generated output files.

Claude and other existing provider implementations may remain as stale last-known-working internal code unless they are required for shared infrastructure. The v1 public bridge surface must not advertise them. Gemini may follow after the ChatGPT path is proven.

## Boundary

Code MCP owns approved repository, filesystem, command, build, test, and other local capabilities. The Web LLM Bridge owns authenticated provider-session transport, run/turn correlation, constrained provider-mode selection, completion extraction, and bounded capture of provider-originated outputs. The caller owns delegation policy and acceptance.

The bridge must not accept caller-local attachments, arbitrary caller paths, context bundles, watch folders, filesystem scans, generic uploads, artifact ingestion, arbitrary navigation, generic authenticated-page reads, or arbitrary JavaScript execution.

Provider-originated output capture is a distinct allowed capability. Files or images generated by ChatGPT for the exact assistant turn associated with a run may be downloaded into a private bridge-owned per-run cache and returned as result artifacts.

## Public v1 contract

```text
delegate({ provider: "chatgpt", key, prompt, mode, outputPolicy })
  -> { runId, key, state }

status({ runId })
  -> queued | sending | working | needs_login | needs_captcha
   | needs_tool_confirmation | completed | failed | cancelled

result({ runId })
  -> rawResponse, completion, selection, artifacts, warnings

stop({ runId })
```

`key` identifies a stable reusable ChatGPT conversation. `runId` identifies one delegation. Runs for the same key are serialized so two active sends cannot race in one conversation.

For v1, `outputPolicy` is intentionally narrow:

```text
none | capture
```

The caller does not choose an output directory, source URL, local input path, or cache limits.

## ChatGPT mode contract

The public mode is a constrained semantic enum rather than arbitrary DOM selector text or assumed internal model IDs:

```text
current | instant | medium | high | extra_high | pro | pro_standard | pro_extended
```

`current` leaves the signed-in UI selection unchanged. The premium values account for currently documented picker variants; the bridge must not assume that all of them exist for every plan, workspace, or rollout. Explicit selections must be verified against the observable ChatGPT picker state. If the requested option is not available or cannot be verified, the run fails with an explicit unavailable or incompatible selection error rather than silently substituting another mode.

The result records requested selection, observed picker/effective information when available, and whether verification succeeded. The bridge must not overclaim an internal model or reasoning level that the UI does not expose.

## Run and turn correlation

Each run follows this lifecycle:

1. Capture the relevant pre-send ChatGPT user-turn and assistant-turn state.
2. Apply and verify the requested mode when it is not `current`.
3. Send the prompt.
4. Confirm that exactly one new user turn was accepted before any fallback submission path is allowed to continue.
5. Bind the run to the assistant turn following that user turn.
6. Wait through active generation, tool-use, login, CAPTCHA, and approval states.
7. Finalize only that assistant turn; never fall back to generic page text for ChatGPT completion.
8. Extract response text, completion metadata, and provider-originated artifacts only from that turn.
9. Store the terminal run result independently from caller acceptance.

Login, CAPTCHA, and Code MCP write/tool confirmations remain human handoffs. The bridge must not bypass CAPTCHA or automatically approve consequential tool actions.

## Completion contract

A successful provider transport is distinct from successful completion-contract parsing and from caller acceptance. Delegated prompts should require a versioned final completion block. The bridge returns the raw assistant response even when parsing fails.

A missing or malformed completion block on an otherwise finalized assistant turn produces a completed transport result with `completion: null` and a warning such as `completion_contract_missing` or `completion_contract_invalid`; it does not rewrite transport completion into a generic failure.

## Provider-originated output cache

Output capture must satisfy all of the following:

- correlate every artifact to the exact assistant turn and `runId`;
- use browser-session-aware download/capture rather than arbitrary unauthenticated Node fetching;
- never accept arbitrary URLs from the caller;
- enforce server-owned limits for artifact count, per-file size, and aggregate run size;
- sanitize file names and prevent traversal or overwrite collisions;
- validate MIME/content as practical before exposing metadata;
- compute SHA-256 for every retained artifact;
- use private filesystem permissions where supported;
- apply TTL cleanup to the private per-run cache;
- return cache paths and metadata, not cookies, credentials, or persisted signed source URLs;
- never accept a caller-specified output directory or input file path.

## Execution sequence

1. **Documentation boundary correction.** Replace the blanket artifact prohibition with the bounded provider-originated output policy and record this complete plan. No source deletion.
2. **Fresh baseline verification.** Install project dependencies and run the full baseline suite so later regressions have a clean reference point.
3. **ChatGPT send/completion reliability.** Port the narrowly relevant behavior and tests from upstream PR #57: authoritative new-user-turn send confirmation, ChatGPT-specific assistant-turn extraction, transient-state handling, and finalized-turn checks.
4. **ChatGPT explicit send fallback.** Evaluate and, if still reproducible, add the ChatGPT-specific direct send-button path described by upstream issue #60 while retaining conservative fallbacks.
5. **Run lifecycle and turn correlation.** Add a long-lived run registry, unique `runId`, per-key serialization, exact user/assistant turn binding, run-scoped status, and run-scoped stop. Keep this internal until stable.
6. **ChatGPT mode adapter.** Add the constrained mode enum, picker interaction, verification, and explicit unavailable/incompatible errors.
7. **Completion parsing and provider-output capture.** Add versioned completion parsing plus private per-run browser-session-aware artifact capture with limits, hashes, permissions, and TTL cleanup.
8. **ChatGPT-only public surface.** Expose `delegate`, `status`, `result`, and `stop` with `provider: "chatgpt"`; stop advertising current generic/local-capability tools without broadly deleting stale provider implementations.
9. **Signed-in end-to-end proof.** Prove ChatGPT selection -> prompt -> Code MCP work -> finalized assistant turn -> completion parse -> generated temporary file capture -> caller result.
10. **Post-proof reduction.** Only after the end-to-end proof, incrementally delete now-unreachable context packing, upload, watch-folder, arbitrary navigation/read, generic artifact-ingestion, and other obsolete implementation paths.

Public-surface narrowing and internal module deletion remain separate changes. Every source slice must have focused tests and should remain independently reviewable.
